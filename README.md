Ress - Debb Enterprise: Storefront & Order API
A website (not a native app) served by a Node.js server, with a Postgres database on Neon and email via Resend. Phones and desktops use it through the browser.

Run locally
cp .env.example .env         # then fill in DATABASE_URL (a dev database, never production)
npm install
npm run build                # builds styles.css and copies Font Awesome into public/
npm start                    # http://localhost:3000   admin: http://localhost:3000/admin

Without ADMIN_TOKEN a random token is printed at startup. Without MAIL_API_KEY, verification and reset links are printed to the console.

Test
Tests wipe every table, so they require their own database. A local Postgres in Docker works well:

docker run -d --name ress-pg -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=ress_test -p 5544:5432 postgres:16-alpine
TEST_DATABASE_URL=postgres://postgres:postgres@localhost:5544/ress_test npm test      # 37 API tests
DATABASE_URL is deliberately not read by the tests. For a Neon dev branch, use its URL as TEST_DATABASE_URL and add TEST_DATABASE_SSL=true. Never point the tests at the main or production branch.

Browser test (needs Google Chrome installed, and a second database that it wipes):

docker exec ress-pg psql -U postgres -c "CREATE DATABASE ress_e2e;"
E2E_DATABASE_URL=postgres://postgres:postgres@localhost:5544/ress_e2e node test/e2e.mjs   # 11 checks
It covers checkout, sign-up and verification, cancellation, password reset and the admin portal.

Deploy (Neon + Render)
Neon: create a project. Copy the connection string (postgresql://…?sslmode=require). The app creates its tables on first boot.
Resend: create an account, verify a sending domain, and create an API key. Use an address on that domain as MAIL_FROM.
Render: create a Web Service from this repository. render.yaml sets the build and start commands. Fill in the sync: false values in the dashboard:
Variable	Value
DATABASE_URL	Neon connection string
APP_URL	https://your-service.onrender.com (or your domain). Must start with https://
MAIL_API_KEY	Resend API key. Optional for now (see below)
MAIL_FROM	Ress - Debb <no-reply@yourdomain.com>. Needed only with MAIL_API_KEY
ADMIN_TOKEN	Generated by Render. Copy it from the dashboard and store it in your password manager
NODE_ENV=production, DATABASE_SSL=true and TRUST_PROXY=1 are already set in render.yaml. In production the app refuses to start if DATABASE_URL, a 32+ character ADMIN_TOKEN or an https:// APP_URL is missing.

Backups: add the Neon connection string as a GitHub repository secret named DATABASE_URL. The workflow in .github/workflows/backup.yml dumps the database nightly and keeps the artifact for 30 days. Neon's free plan keeps only about 6 hours of point-in-time history, so this dump is your real safety net. For longer retention, copy the dumps to object storage (Cloudflare R2, S3 or Backblaze B2). Run scripts/backup.sh by hand to make an ad-hoc dump.
Payments
Pay on delivery is the default. The order is marked paid when the admin sets it to Delivered.
Bank transfer appears at checkout only when BANK_TRANSFER_DETAILS is set. Customers see the details on their receipt. The admin uses Mark paid once the money arrives.
Card payments are not included yet. They need a gateway account. For Nigeria, Paystack or Flutterwave are the usual choices. Adding one means a merchant account, its API keys, and a webhook endpoint.
Products
Admins add, edit and delete products in the admin portal.
Deleting a product with no orders removes it. A product that appears in past orders is archived instead: hidden from the shop, kept for order history, and restorable.
Products with zero stock are hidden from the shop. Admins still see them.
Install as an app (PWA)
The site can be installed on phones and computers. In Chrome or Edge on Android and desktop, an Install app button appears in the header. On iPhone, use Share → Add to Home Screen. The service worker caches the site shell so the app opens without a connection. It never caches stock, prices or order data.

Running without email
MAIL_API_KEY is optional. Without it in production:

Sign-up creates a verified account straight away, so customers can log in at once. Nothing is emailed.
"Forgot password" is switched off. Customers are told to contact you on WhatsApp.
Add MAIL_API_KEY and MAIL_FROM later (Resend, with a verified domain) to turn verification and reset back on. No code change is needed.

Admin token
Use the value Render generated, or any random value of 32+ characters: node -e 'console.log(require("crypto").randomBytes(32).toString("hex"))'.
It lives only in the host's environment settings. Never commit it or put it in .env in the repository.
Rotate it by changing ADMIN_TOKEN and redeploying. Anyone holding it has full admin access, and there is no per-person audit trail beyond order history.
What the API covers
Level	Where
1. Catalogue, cart, order, lookup by RDE-XXXXXX	GET /api/products, POST /api/orders, GET /api/orders/:id
2. Accounts, email verification, password reset, validation	/api/auth/*, server/validation.js
3. Cancellation and stock	POST /api/orders/:id/cancel: Pending or Processing only. Stock is restored in the same transaction
4. Idempotency and history	Idempotency-Key header on POST /api/orders; GET /api/orders?status=active|completed|cancelled&page=&pageSize=
5. Rate limits and admin	Per-IP limits on order create, cancel, lookup and auth. /admin portal: order status changes, and add/edit products and their photos (/api/admin/products, /api/admin/products/:id/image)
Rules worth knowing
Stock is safe under concurrency. Each order locks its product rows (SELECT … FOR UPDATE) inside a transaction, and the database rejects negative stock with a CHECK constraint. Two buyers cannot take the last unit.
Order IDs are RDE- followed by 6 random digits (900,000 possible IDs). Each is checked against the database before use. Widen the format before reaching a few hundred thousand orders.
Guest orders can be cancelled only with the phone number used at checkout. Account orders can be cancelled only by their owner.
Public lookup shows status and items, plus the customer's first name. Phone and address are never shown.
Accounts must verify their email before logging in. Reset links expire after 1 hour and work once. A reset logs out every session.
Sessions and one-time tokens are stored as SHA-256 hashes, never in plain text.
Security and known limitations
HTTPS: the app sends HSTS in production. Render provides HTTPS. Do not serve the site over plain HTTP.
Security headers are set on every response: CSP (self-hosted scripts and styles only), nosniff, X-Frame-Options: DENY, a strict referrer policy and a permissions policy.
Inline scripts remain allowed (script-src 'unsafe-inline') because the pages use inline onclick handlers. Removing this needs a refactor to delegated event listeners. All user data is escaped before it is rendered.
Rate limits are in memory. They reset on restart and are per instance. Use a shared store if you run more than one instance.
Single-dyno assumption: the server itself is stateless (sessions and orders are in Postgres), so you can scale out. Rate-limit counters are the only per-instance state.
Not included yet: card payments, customer-facing order emails, a staff login system (admin uses one shared token), product images, and store-listed apps (Play Store and App Store).
